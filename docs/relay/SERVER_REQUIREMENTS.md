# Сервер в Нидерландах для приёмника Telegram: требования и проверка

Документ для владельца/администратора сервера. Дата: 27.11.2026.
Проект: Telegram Зеркало, [репозиторий](https://github.com/OlgaIL/telegram-site-mvp).

**Задача сейчас — выяснить, подходит ли существующий сервер. Покупать новый, переустанавливать
этот сервер или менять работающие сервисы на нём до проверки не требуется.**

## 1. Что будет работать на сервере

Небольшой фоновый процесс получает новые публикации и правки из Telegram-каналов через Bot API,
скачивает фотографии, сохраняет события в локальной очереди SQLite и передаёт их по HTTPS
на существующий сайт `https://tg4you.ru` в РФ. Если сайт недоступен — хранит очередь и повторяет отправку.

```text
Telegram Bot API ← исходящий HTTPS ← приёмник в Нидерландах
                                      │
                                      └─ исходящий HTTPS → tg4you.ru в РФ
```

На зарубежный сервер **не переносим** сайт, пользовательскую базу PostgreSQL, почтовую
авторизацию и Word2you. На нём не нужны Next.js и сервер публичных веб-страниц.
Это обычный клиент Telegram Bot API, без предоставления сетевого доступа другим пользователям.

На старте — 3–5 каналов, текст и отдельные фото. Альбомы, видео и документы пока вне задачи.
Оценка нагрузки ниже — инженерный ориентир для беты, не результат нагрузочного замера.

## 2. Ресурсы

| Параметр | Достаточно для отдельной небольшой VM | Желательно / замечания |
|---|---|---|
| CPU | 1 vCPU | 2 vCPU с запасом; важнее отсутствие постоянной загрузки соседями |
| RAM | 1 ГБ всего для отдельного Linux-сервера | 2 ГБ комфортнее при установке пакетов и обновлениях |
| Диск | 15 ГБ SSD/NVMe всего на отдельном сервере | 20–30 ГБ с запасом; persistent storage, не временный диск |
| Свободное место под приложение/очередь/фото | Выделить не менее 5 ГБ после установки ОС | Лучше 10 ГБ; мониторить свободное место и заранее расширять |
| Сеть | Устойчивый исходящий HTTPS к Telegram и к сайту в РФ | 10 Мбит/с достаточно как ориентир; стабильность важнее скорости порта |
| Трафик | Для первых каналов ожидаются небольшие объёмы | Желательно хотя бы 10 ГБ/месяц доступного остатка; уточнить стоимость превышения |
| Режим работы | 24/7, без сна и автоматического выключения | Автозапуск службы после перезагрузки |
| Архитектура CPU | x86_64 — основной проверяемый вариант | arm64 возможен после проверки зависимостей SQLite; 32-bit не планируется |

**Если на сервере уже работают другие проекты:** смотреть надо на свободные ресурсы и ограничения,
а не только на общий тариф. Желательно выделить приёмнику 1 vCPU и около 1 ГБ доступной RAM,
5–10 ГБ постоянного диска. Не отбирать эту память у существующих сервисов и не рассчитывать на swap
как на замену RAM. Сервер с 8 ГБ RAM, полностью занятыми другими задачами, может не подойти.

Посты хранятся в очереди до доставки, доставленные события — 30 дней, доставленные фото — 7 дней.
Если РФ-сайт недоступен долго, недоставленная очередь продолжает расти; нужен контроль диска,
а не безусловное обещание «5 ГБ хватит навсегда».

## 3. ОС и способ размещения

Предпочтительно **Ubuntu Server 24.04 LTS, 64-bit, с systemd**.
Существующий поддерживаемый Debian/Ubuntu тоже можно рассмотреть после проверки версии.
Не нужно переустанавливать работающий сервер только ради совпадения дистрибутива.

Подходит VPS, VM или физический сервер. Сам факт расположения в Нидерландах не доказывает
связь с Telegram: доступность проверяем изнутри конкретного сервера.

На общем сервере предпочтительна отдельная VM или системный пользователь + отдельная systemd-служба
с лимитами ресурсов. Если администратор использует только Docker, это допустимый вариант для обсуждения,
но текущий основной план — systemd. Для Docker потребуются отдельная инструкция, постоянные volumes
для SQLite и фото, корректное завершение процесса и автозапуск. Контейнер без постоянного volume не подходит.

## 4. Какой доступ нужен

### Для оценки пригодности

Достаточно ответов администратора и вывода команд из раздела 10. SSH-доступ разработчику
для первоначального решения не обязателен. Можно вообще сначала не выдавать доступ.

### Для установки

Нужен один из двух вариантов:

1. **Администратор сам выполняет подготовленные команды.** Тогда доступ разработчику не требуется.
2. **Выделенный пользователь для установки**, например `tg4you-deploy`, вход по отдельному SSH-ключу.
   Повышение прав требуется только для согласованных действий: установка runtime/пакетов,
   создание пользователя службы, каталогов, systemd unit, расписания копий и их обслуживания.

Постоянный root-доступ и пароль владельца хостинга для разработки не нужны. Не требуется доступ
к базам, папкам, токенам или панелям других проектов мужа. Конкретный способ ограниченного sudo
администратор выбирает под свою систему; редактирование привилегированного unit-файла — тоже
административное действие, его нельзя считать безопасным безусловным доступом к чужому серверу.

Сама служба запускается от **отдельного непривилегированного пользователя** `tg4you-relay`,
без интерактивного входа. Тестовый и основной боты получают разные каталоги данных и конфигурации.

Вход можно организовать через существующий bastion/административный VPN или ограниченный SSH.
Открывать новый SSH-порт всему интернету не требуется. Если будет прямой SSH, сообщить адрес,
порт и имя выделенного пользователя; открытый ключ передадим отдельно. Приватный ключ остаётся у владельца.

## 5. Сеть, IP и порты

| Направление | Что требуется | Зачем |
|---|---|---|
| Исходящий TCP 443 | `api.telegram.org` | getMe, getUpdates, getFile и скачивание файлов Telegram |
| Исходящий TCP 443 | `tg4you.ru` | передача событий, фото и heartbeat в РФ |
| Исходящий TCP 443 | `hc-ping.com` либо фактический домен выбранного мониторинга | независимый сигнал работоспособности |
| DNS | Доступ к штатному DNS-резолверу сервера | разрешение имён; обычно UDP/TCP 53, либо уже настроенный другой способ |
| Синхронизация времени | Работающий штатный NTP/chrony/systemd-timesyncd | подпись запросов проверяет время; часто исходящий UDP 123 |
| Установка/обновления | Доступ к выбранным официальным репозиториям ОС, Node.js, npm, при необходимости GitHub | установка приложения и обновлений; адреса зависят от способа развёртывания |
| Входящий SSH | Только для администрирования выбранным способом | установка, логи, обновления; порт может быть не 22 |

Приложение получает события через **long polling** — само делает исходящий getUpdates.
Поэтому **входящие 80/443, домен, nginx и HTTPS-сертификат на приёмнике не нужны**.
Локальные ограничения сети могут требовать согласования исходящих соединений; текущие правила
firewall не отключать и не заменять целиком.

**Выделенный публичный IPv4 не обязателен:** достаточно рабочего исходящего IPv4 через NAT
и согласованного способа SSH-доступа. Статический исходящий IP удобен для диагностики и возможного
будущего allowlist, но не является требованием текущего протокола. Это уточняет более ранний
список пожеланий при аренде новой VM. IPv6-only пока не принимаем без отдельной сетевой проверки.

Обычный HTTP-прокси, если он обязателен в этой инфраструктуре, нужно обсудить до установки:
текущий пробник и проектный план не гарантируют автоматическую работу через заданный прокси.
Проверку TLS-сертификатов не отключать. Списки IP Telegram не закреплять вслепую как единственный
способ доступа: адреса могут меняться, правила должен сопровождать администратор.

## 6. ПО

| Компонент | Требование | Кто готовит |
|---|---|---|
| Node.js | Поддерживаемая ветка **22.x**, актуальный patch; npm соответствующей установки | Администратор, по согласованной инструкции |
| systemd | Запуск отдельной службы, автоматический restart, журнал | Обычно уже есть в Ubuntu/Debian |
| SQLite | Локальная файловая БД с WAL; библиотека входит в приложение | Разработчик фиксирует библиотеку/версию |
| CA certificates | Актуальное системное хранилище доверенных сертификатов | Администратор/обновления ОС |
| curl, tar | Сетевые проверки и работа с архивом приложения | Администратор, если отсутствуют |
| SSH/SFTP либо SCP | Выдача доступа и доставка приложения | Администратор |
| Резервное копирование и таймер | Ежедневная копия на независимый носитель, контроль результата | Совместно с администратором |

PostgreSQL, Redis, RabbitMQ, PM2, nginx и Docker **для выбранной схемы приёмника не требуются**.
Git удобен для получения кода, но не обязателен: можно передавать проверенный архив релиза.
Системный sqlite3 CLI полезен для диагностики, но приложение не обязано вызывать его напрямую.
Python, make и C/C++ compiler могут понадобиться, если выбранная Node-библиотека SQLite
не имеет подходящего готового бинарного пакета; заранее ставить их на чужой сервер не требуется.

Node.js другой версии, нужный существующим проектам, **не заменяем глобально**.
При необходимости ставим отдельный runtime для приёмника и указываем абсолютный путь в systemd.
Команда `apt install nodejs` сама по себе не гарантирует Node 22. Обновление версии согласуем
после проверки зависимостей, не устанавливаем произвольный «самый новый» Node вместо проектного.

## 7. Файлы, права и секреты

Предлагаемая структура; администратор может согласовать эквивалентные пути:

| Путь | Содержимое |
|---|---|
| `/opt/tg4you-relay/releases/<version>/` | код приложения/зависимости, read-only для пользователя службы |
| `/opt/tg4you-relay/current` | ссылка на выбранный релиз |
| `/etc/tg4you-relay/test.env` | настройки только тестового бота |
| `/etc/tg4you-relay/main.env` | настройки основного бота после отдельного переключения |
| `/var/lib/tg4you-relay/test/` | SQLite, фото и очередь тестового бота |
| `/var/lib/tg4you-relay/main/` | отдельные SQLite, фото и очередь основного бота |
| journald | ограниченные по объёму журналы без токенов/текстов публикаций |

Настройки включают токен бота, ожидаемый bot_id, URL доставки, секрет HMAC и адрес
независимого мониторинга. Их предоставит владелец проекта по защищённому каналу, а не через
GitHub/публичную задачу. Для первой пробы используется только `@tg4you_local_test_bot`.
Токен основного бота не нужен для оценки пригодности сервера.

EnvironmentFile читается systemd; root-owned файл с правами 600, без публикации в Git.
Каталог данных приватный, владелец — пользователь службы. При иной схеме запуска права
подбираются администратором так, чтобы приложение могло работать без доступа других пользователей.
Никаких токенов в командной строке, логах, снимках экрана или URL, передаваемых в переписке.

На сервере будет временная копия содержимого публикаций, а не только безобидный технический счётчик.
Доступ администратора/root к этой машине означает техническую возможность прочитать и эти данные,
и секреты приложения. Для чужих/закрытых каналов место обработки согласуется с владельцем проекта.

## 8. Сохранность и эксплуатация

- Постоянный локальный диск, корректные fsync/rename и файловые блокировки. SQLite с WAL не размещать
  на случайной общей NFS/SMB-папке. Для Docker нужен локальный persistent volume с подходящими свойствами.
- Служба автоматически запускается после reboot, перезапускается после сбоя, корректно получает SIGTERM.
- Один опросчик на один токен; два независимых процесса с одним ботом одновременно не запускать.
- Обновления ОС/перезагрузки сервера согласуются с владельцем проекта; желательно предупредить о работах.
- Нужны контроль свободного диска, очереди, свежести успешного опроса и независимое уведомление на почту.
- Ежедневная согласованная копия SQLite **с учётом WAL**, например через штатный backup API,
  с отправкой на отдельный носитель/хранилище. Копия рядом на том же диске не защищает от его потери.
- На старте разумно хранить 7 ежедневных копий с ротацией; объём/стоимость уточняются по фактическим данным.
  Медиа и конфигурация должны иметь отдельный план восстановления: одна копия SQLite не содержит JPEG-файлы.
- До основного бота провести тест восстановления на изолированном стенде. Нельзя проверять аварию
  заполнением общего диска или отключением чужих сервисов.
- Ежедневная копия допускает потерю до суток последних неподтверждённых сайтом данных при гибели
  диска приёмника. Это не обещание нулевой потери при любой аварии.

Telegram хранит неполученные события не дольше 24 часов. Поэтому длительный простой приёмника
может потерять публикации, даже если сам сайт в РФ работает. Важно не только выделить CPU/RAM,
но и обеспечить постоянную работу и получение уведомлений о сбое.

## 9. Проверка пригодности перед установкой основного сервиса

Проверяем **с этого сервера**, а не с телефона или компьютера с VPN:

1. Реальные getMe тестового бота: ориентир 60/60 успешных за час.
2. Запросы к `https://tg4you.ru/health`: минимум 99% за сутки, ответ <2 секунд.
   Для 1440 проверок это минимум 1426 успешных. Это ориентир принятия площадки, не SLA провайдера.
3. Текст и одно фото из тестового канала действительно приняты и сохранены пробником.
4. На следующем этапе — реальный подписанный POST события и PUT фото на **стендовый** backend.
   Один успешный GET /health не доказывает работоспособность всего пути.
5. Перезапуск и восстановление копии — в отдельной среде, не через остановку остальных сервисов сервера.

Пробник подготовим/передадим вместе с инструкцией. Он проверяет имя тестового бота и не меняет webhook.
Код основного приёмника ещё разрабатывается; этот документ не означает, что достаточно включить
готовую службу прямо сейчас. Сначала требуется оценка сервера и проверка сети.

## 10. Что можно прислать для оценки

Достаточно сообщить ОС, архитектуру, общие/свободные CPU/RAM/диск, ограничения сети и доступов,
наличие других проектов. Если удобно, администратор может выполнить команды ниже.
**Это команды чтения, они ничего не устанавливают и не перезапускают.**

```bash
cat /etc/os-release
uname -m
nproc
uptime
free -h
df -hT /
node --version
npm --version
systemctl --version | head -n 1
timedatectl status
```

Если данные планируется хранить на другом диске, отдельно выполнить `df -hT /путь/к/нему`.
Ошибки «node/npm/systemctl not found» не скрывать — это просто означает, что компонент отсутствует.
Для контейнера эти команды показывают среду контейнера; лимиты CPU/RAM/volume нужно уточнить у администратора.

Необязательные начальные сетевые проверки без токена:

```bash
curl -4 -I --connect-timeout 5 --max-time 10 https://api.telegram.org/
curl -4 --connect-timeout 5 --max-time 10 https://tg4you.ru/health
```

Для корня api.telegram.org редирект сам по себе не ошибка: здесь проверяется соединение HTTPS,
а не успешность Bot API. Для сайта ожидается HTTP-успех и JSON `{"status":"ok"}`.
Это разовые проверки, они не заменяют суточный замер и тест с ботом.
При передаче вывода можно скрыть hostname, внутренние адреса и пути других проектов.
Не присылать `.env`, дамп окружения, закрытые ключи, токены и файлы конфигурации чужих сервисов.

## 11. Короткий ответ администратора (можно скопировать)

```text
1. Тип сервера / провайдер / фактическая локация:
2. ОС и версия, архитектура CPU:
3. Всего CPU/RAM/диска, сколько свободно и сколько можно выделить приёмнику:
4. Какие ограничения CPU/RAM/диска установлены для пользователя/VM/контейнера:
5. Работает ли 24/7, бывают ли выключения/перезагрузки:
6. Есть ли другие проекты, можно ли выделить отдельную VM или пользователя/systemd-службу:
7. Есть ли Node 22, можно ли установить отдельный runtime без изменения других проектов:
8. Есть ли исходящий IPv4/NAT и HTTPS к Telegram и tg4you.ru, нужны ли proxy/allowlist:
9. Как организован административный доступ: SSH/порт/bastion, кто выполнит установку:
10. Можно ли создать отдельную службу и приватные постоянные каталоги:
11. Есть ли независимое место для резервных копий и кто контролирует восстановление:
12. Какие лимиты трафика и дополнительные расходы:
```

Адрес доступа и открытые ключи можно передать отдельно; пароли и приватные ключи в этот ответ не включать.
По этим данным решим, можно ли использовать существующий сервер и какие приготовления нужны.

## 12. Основания технических требований

- [Node.js: поддерживаемые ветки и рекомендации для production](https://nodejs.org/en/about/previous-releases).
- [SQLite: согласованная резервная копия работающей базы](https://www.sqlite.org/backup.html).

Ресурсы и критерии сети в этом документе — оценка нашего проекта для небольшой беты;
это не официальные минимальные требования Telegram/Node.js и не гарантия доступности выбранного сервера.
