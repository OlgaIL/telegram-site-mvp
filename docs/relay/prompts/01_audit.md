# Задание 01 — аудит кода и согласование контракта

Сначала прочитай `docs\relay\prompts\00_COMMON.md` целиком. Его запреты действуют здесь.

## Контекст

Архитектор составил черновик контракта между приёмником и основным backend по коду коммита `32f72a7`
и нашёл 10 рисков в Telegram-цепочке. Ни одно утверждение не проверено запуском. Твоя работа — проверить и зафиксировать.

## Точная задача

1. Проверить каждую находку из списка ниже: подтвердить или опровергнуть с указанием `файл:строка` и, где возможно, тестом или запуском на локальной базе.
2. Проверить идемпотентность текущей обработки в трёх ситуациях: повтор одного события; два одинаковых события одновременно; `channel_post`, пришедший после `edited_channel_post` того же сообщения.
3. Сверить `docs\relay\CONTRACT_DRAFT.md` с фактической схемой базы и кодом. Закрыть шесть вопросов из его раздела 7.
4. Выпустить `docs\relay\CONTRACT.md` версии 1: полный текст контракта, без ссылок «см. черновик».
5. Составить карту файлов: какие файлы будут править задания 02, 03, 04, чтобы они не пересекались.

Находки для проверки:
1. `server/routes/telegram.routes.js` — при исключении возвращается HTTP 200.
2. Там же — при пустом `TELEGRAM_WEBHOOK_SECRET` проверка секрета пропускается.
3. `server/services/media.service.js` — ошибка скачивания проглатывается; повтора для `media_status='error'` нет нигде.
4. `server/telegram/telegram-file.service.js` — `fetch` без таймаута; скачивание внутри обработки webhook.
5. `server/repositories/posts.repository.js` — upsert без защиты порядка; поздний `channel_post` затирает текст и обнуляет `edited_at`.
6. Правка поста с фото при сбое скачивания перезаписывает `media_url` в `null`.
7. `update_id` нигде не сохраняется.
8. `TELEGRAM_PROXY_URL` объявлен в `server/config/env.js`, но не используется; `createBot()` нигде не вызывается.
9. Тестов Telegram-цепочки нет.
10. `/health` не проверяет базу и свежесть данных.
