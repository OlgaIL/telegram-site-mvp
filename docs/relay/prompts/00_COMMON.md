# Общие правила для всех агентов проекта «Telegram Зеркало — приёмник»

Этот файл читается первым в каждом задании. Он не является отдельным заданием.

## Контекст

«Telegram Зеркало» (https://tg4you.ru) сохраняет публикации Telegram-каналов и показывает их на сайте.
Репозиторий: `C:\Users\olgak\PROJECTS\telegram-site-mvp` (GitHub `OlgaIL/telegram-site-mvp`).
Стек: Node.js 22, Express 5, PostgreSQL через `pg`, Next.js 16, Pino, nginx, PM2. Разработка на Windows / PowerShell.

Проблема: webhook Telegram не доходит до production-сервера в РФ (TCP-рукопожатие не завершается),
исходящие запросы сервера к Telegram API падают частично. Причина не установлена и для задания не важна.

Решение: отдельный маленький процесс-приёмник на сервере вне РФ.
Он опрашивает Telegram (`getUpdates`), сохраняет сырые события в SQLite до подтверждения, скачивает фото
и отправляет события и файлы на основной backend по HTTPS с подписью HMAC.
Основной backend к Telegram не обращается вообще.

Документы, которые нужно знать:
- `docs\relay\CONTRACT.md` — согласованный контракт (если его ещё нет — `docs\relay\CONTRACT_DRAFT.md`);
- `docs\relay\AUDIT.md` — результат аудита (появляется после задания 01).

## Запреты — действуют всегда

1. Не подключаться к production-серверу, production-базе и не менять их. Серверные команды выполняет только Ольга.
2. Не трогать Word2you: его процесс `myworld-server`, порт 4000, его nginx, базу, файлы.
3. Не менять конфигурацию nginx. Новые маршруты живут под `/telegram/`, который уже проксируется.
4. Не трогать основного бота `@Test_site_mvp_bot`: не вызывать `setWebhook`, `deleteWebhook`, `getUpdates` с его токеном.
   Для проверок есть только тестовый бот `@tg4you_local_test_bot`.
5. Никогда не использовать `drop_pending_updates`.
6. Не отключать проверку HTTPS-сертификатов. Не ослаблять существующую авторизацию.
7. Секреты не писать в код, в Git, в отчёты и в чат. Не просить Ольгу прислать `.env`. В примерах — только заглушки вида `<BOT_TOKEN>`.
8. Не делать покупок и не создавать учётных записей.
9. Не сливать в `main` и не пушить в `main`. Ветка задания указана в самом задании.
10. `git add -A` и `git add .` запрещены — только явные пути. Чужие файлы не форматировать и не переименовывать.
11. Править только файлы из раздела «Допустимые изменения» своего задания. Нужен другой файл — остановиться и написать об этом в отчёте.
12. Контракт `docs\relay\CONTRACT.md` не менять. Нужна правка — остановиться и описать её в отчёте.

## Перед началом работы

1. `git status`, `git branch --show-current`, `git log --oneline -3`. Незакоммиченные чужие изменения не трогать и не терять.
2. Убедиться, что базовый коммит — `32f72a7` (ветка `codex/email-auth`) или ветка, указанная в задании.
3. Сказать в двух-трёх строках, что понял, и начать. Вопросы Ольге — только если без ответа нельзя продолжать, одним списком.

## Расход и субагенты

- Если запускаешь субагентов: только узкие типы под задачу, модель указывать явно; поиск и прогон тестов — младшая модель, код — средняя.
- Субагент: не больше 40 вызовов инструментов, затем стоп и отчёт. Эти цифры вписывать в промпт субагента.
- Вывод команды в контекст — не больше 100 строк. Длинное — в файл, читать хвост или поиском.
- Команды дольше 5 минут — в фоне.

## Отчёт

В конце — файл отчёта по пути из задания, с названием своей модели в имени файла. В отчёте:
что сделано; какие файлы изменены; какие проверки запущены и их фактический вывод (коротко);
что не сделано и почему; допущения, принятые самостоятельно; что должна сделать Ольга.
Упавшие тесты не скрывать и не «чинить» ослаблением проверок.
