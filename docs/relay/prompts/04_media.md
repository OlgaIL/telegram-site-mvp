# Задание 04 — фотографии: скачивание на приёмнике, приём на backend

Сначала прочитай `docs\relay\prompts\00_COMMON.md`, `docs\relay\CONTRACT.md`, `docs\relay\AUDIT.md`
и отчёты заданий 02 и 03 в `docs\relay\reports\`.

## Контекст

Задания 02 и 03 слиты в одну ветку: текстовые события проходят путь «Telegram → приёмник → backend → база».
Фото пока помечаются `pending` и не скачиваются. Сейчас фото скачивает сам backend внутри обработки webhook,
без таймаута и без повторов, а при сбое правка подписи стирает уже скачанное фото.
После этого задания фото скачивает только приёмник.

Это задание правит обе стороны, поэтому выполняется одним агентом и строго после слияния 02 и 03.

## Точная задача

### Приёмник (`relay/`)

1. Для события с фото выбрать самый большой размер (логика как в `selectLargestPhoto` из `server/services/media.service.js`).
2. `getFile` → скачивание с таймаутом 30 с → файл `<file_unique_id><ext>` в `RELAY_DATA_DIR/media/`, SHA-256, размер. Запись через временный файл и переименование.
3. Повторы: 5 с, 30 с, 2 мин, 10 мин, затем раз в час до 24 часов; потом `failed`. Истёкшая ссылка — повторный `getFile`. Не чаще одного `getFile` в секунду.
4. Отправка файла: `PUT /telegram/ingest/media/<file_unique_id>` по разделу 2.2 контракта, таймаут 60 с, те же правила повторов, что у событий.
5. **Текст не ждёт фото.** Фото не готово за 2 минуты → событие уходит с `state: "pending"`. Готово раньше → сначала файл, затем событие с `state: "ready"`.
   Файл, скачанный позже, отправляется сам по себе.
6. Один `file_unique_id` скачивается и отправляется один раз, сколько бы событий на него ни ссылалось.
7. Файл на приёмнике удаляется через 7 дней после подтверждённой отправки.
8. Файл больше 10 МБ не отправляется: `failed` с причиной, событие уходит без фото.

### Backend (`server/`)

1. Маршрут `PUT /telegram/ingest/media/:fileUniqueId` по разделу 2.2 контракта: подпись, потоковая запись во временный файл,
   сверка SHA-256, переименование в `UPLOADS_DIR`, затем обновление всех постов с этим `telegram_file_unique_id`.
   Имя файла строится только из проверенного `file_unique_id` (символы `A-Za-z0-9_-`) и расширения из белого списка — никакого выхода из каталога.
2. Событие с `state: "ready"` или с уже лежащим на диске файлом → `media_status='downloaded'`; иначе `pending`; `failed` → `error`.
3. Backend перестаёт обращаться к Telegram: скачивание в `server/services/media.service.js` и `server/telegram/telegram-file.service.js` отключается.
   Старый webhook-маршрут сохраняет пост с `media_status='pending'`.
4. Правка поста не меняет поля фото, если `file_unique_id` тот же; если фото заменено — старое остаётся до прихода нового файла.

## Запреты

Сверх общих: не менять контракт и миграцию 010; не трогать раздачу `/uploads/telegram` и nginx;
не удалять существующие файлы в `UPLOADS_DIR`; не добавлять обработку альбомов, видео и документов.

## Входные данные

Контракт, аудит, отчёты 02 и 03, документация Bot API (`getFile`: срок ссылки и лимит размера — сверить дословно).
В тестах — поддельный Telegram, отдающий файл; реальный токен не нужен.

## Ожидаемые артефакты

Код и тесты по списку; отчёт `docs\relay\reports\04_media_<модель>.md`.

## Проверки

1. Пост с фото: файл на диске backend, `media_status='downloaded'`, файл открывается по `/uploads/telegram/...`.
2. Поддельный Telegram не отдаёт файл 3 минуты → текст опубликован сразу с `pending`; после восстановления фото привязалось без нового события.
3. Файл пришёл раньше события и событие раньше файла → итог одинаковый.
4. Тот же файл отправлен дважды → второй ответ `exists`, файл один.
5. Неверная контрольная сумма → 422, временный файл удалён, пост не изменён.
6. `file_unique_id` вида `../../x` → 4xx, вне `UPLOADS_DIR` ничего не создано.
7. Правка подписи у поста с фото → фото на месте.
8. В коде `server/` не осталось обращений к `api.telegram.org` (проверка поиском).
9. `npm test` в корне и в `relay/` проходят.

## Критерий завершения

Все девять проверок проходят, вывод приведён в отчёте; изменены только разрешённые файлы;
в отчёте указано, нужен ли ещё `TELEGRAM_BOT_TOKEN` на backend (ожидается: нет).
