# Задание 02 — приёмник: опрос Telegram, надёжное хранение, отправка

Сначала прочитай `docs\relay\prompts\00_COMMON.md` и `docs\relay\CONTRACT.md` целиком.
Если `CONTRACT.md` ещё нет, выполняй только часть А и остановись.

## Контекст

Приёмник — отдельный процесс Node.js 22 на сервере вне РФ. Входящих портов у него нет.
Он единственный, кто разговаривает с Telegram. Параллельно другой агент делает приём на основном backend (задание 03) —
вы связаны только контрактом, общих файлов у вас нет.

## Точная задача

### Часть А — пробник (нужен раньше всего, не ждёт контракта)

Файл `relay/probe.mjs`, без внешних зависимостей, до ~100 строк. Читает `BOT_TOKEN` из окружения. Режимы:
- `node probe.mjs reach` — 60 запросов `getMe` с паузой 60 с, таймаут 10 с; в конце — число успешных и медиана времени;
- `node probe.mjs poll` — цикл `getUpdates` (`timeout=50`, `allowed_updates=["channel_post","edited_channel_post"]`),
  печатает тип, `update_id`, чат, `message_id`; для фото вызывает `getFile` и сохраняет файл в `./probe-media/`.
  Если установлен webhook — печатает понятное сообщение и выходит, сам webhook не снимает.
Токен в вывод не попадает.

### Часть Б — приёмник

Пакет `relay/` со своим `package.json`:

1. **Опрос.** Свой цикл `getUpdates`, а не встроенный опрос библиотеки бота: подтверждение должно зависеть от записи на диск.
   Пачка событий и новый `poll_offset` пишутся в SQLite одной транзакцией; следующий запрос уходит с новым `offset`.
   `allowed_updates`: `channel_post`, `edited_channel_post` (и `my_chat_member`, если так решено в контракте).
   Ошибка 409 (опрос из другого места или установлен webhook) — понятная запись в журнал, пауза 30 с, без падения.
2. **Хранилище.** SQLite по разделу 6 контракта, `journal_mode=WAL`, `synchronous=FULL`. Библиотеку выбери сам и обоснуй в отчёте.
3. **Очередь отправки.** Один последовательный поток, строго по возрастанию `update_id`. Отправка по разделу 2.1 контракта с подписью по разделу 4.
   Реакция на ответы — строго по таблице контракта: временный отказ — пауза 1 с → 5 мин со случайной добавкой, очередь стоит;
   422 — после 5 попыток dead-letter, очередь идёт дальше; 401/403 — очередь стоит, повтор раз в 5 минут.
4. **Сигнал «жив».** Раз в 60 с по разделу 2.3 контракта. Дополнительно — GET на `HEALTHCHECK_PING_URL`, если задан.
5. **Очистка.** Доставленные события старше 30 дней удаляются. Dead-letter не удаляется.
6. **Команды:** `relay status` (глубина очереди, старейшее событие, dead-letter), `relay replay --from <id> --to <id>`, `relay dead list`, `relay dead retry <id>`.
7. **Настройки** — только из окружения; `relay/.env.example` с заглушками:
   `BOT_TOKEN`, `INGEST_BASE_URL`, `RELAY_INGEST_KEY_ID`, `RELAY_INGEST_SECRET`, `RELAY_DATA_DIR`, `HEALTHCHECK_PING_URL`.
   Процесс отказывается стартовать без обязательных значений и при `INGEST_BASE_URL` не на `https://` (кроме `localhost` в тестах).
8. **Журнал** — JSON (Pino). Токен, секрет и подпись в журнал не попадают; адреса Telegram с токеном маскируются.
9. **Остановка** по SIGTERM: дождаться конца текущей транзакции и отправки.

Фото в этом задании не скачиваются: событие с фото уходит с `media: [{state:"pending"}]`. Скачивание — задание 04.
Оставь для него точку расширения — отдельный модуль `relay/src/media.js` с заглушкой.

## Допустимые изменения

Только `relay/**` и отчёт. Корневые `package.json` и `package-lock.json` не трогать.

## Запреты

Сверх общих: никакого HTTP-сервера на приёмнике; не хранить очередь только в памяти;
не подтверждать Telegram событие, не записанное на диск.

## Входные данные

`docs\relay\CONTRACT.md`; `docs\relay\AUDIT.md`; документация Bot API. Реальный токен для тестов не нужен: в тестах — поддельный Telegram.
Ручную проверку с тестовым ботом выполняет Ольга на сервере, не ты.

## Ожидаемые артефакты

`relay/package.json`, `relay/probe.mjs`, `relay/src/**`, `relay/test/**`, `relay/.env.example`, `relay/README.md` (запуск локально, переменные, команды),
отчёт `docs\relay\reports\02_relay_<модель>.md`.

## Проверки (в тестах — поддельные Telegram и backend на localhost)

1. Событие получено → записано → только потом ушёл запрос с новым `offset`.
2. Процесс убит между записью и следующим `getUpdates` → после запуска событие получено повторно и не задвоилось.
3. Backend отвечает 500 десять раз, затем 200 → событие доставлено один раз, порядок трёх событий сохранён.
4. Backend отвечает 422 → после 5 попыток событие в dead-letter, следующее доставлено.
5. Backend отвечает 401 → очередь стоит, события не теряются.
6. Подпись совпадает с эталонным вектором из контракта.
7. В журнале и выводе тестов нет токена и секрета (проверка поиском по выводу).
8. `npm test` в `relay/` проходит; `npm test` в корне не сломан.

## Критерий завершения

Все восемь проверок проходят, их вывод приведён в отчёте; `relay/README.md` позволяет запустить приёмник локально против поддельного backend;
в отчёте перечислено, что нужно для задания 04 и что должна сделать Ольга.
