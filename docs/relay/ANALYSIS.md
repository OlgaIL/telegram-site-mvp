## 0. Вопросы, без которых нельзя окончательно выбрать покупку

Архитектуру я выбрал под допущения ниже. Ответы могут её поменять.

1. **Бюджет.** Готова ли Ольга платить около 1 800–1 900 ₽ в месяц за отдельный маленький сервер на время бесплатной беты?
   Если нет — остаются бесплатные варианты Г и Д с более слабыми гарантиями (раздел 2).
2. **Оплата.** Только российские карты и СБП, или есть зарубежная карта? От этого зависит провайдер.
3. **Токен бота за рубежом.** Допустимо ли, что токен основного бота и временные копии постов лежат на сервере вне РФ?
   Есть ли среди первых клиентов закрытые каналы?
4. **Цена сбоя в бете.** Допустимо ли, что при простое приёмника дольше 24 часов посты за это время придётся
   восстанавливать вручную (правкой поста в Telegram)? Если нет — нужен второй приёмник сразу, это ещё столько же в месяц.

**Допущения, пока ответов нет:** бюджет до 2 000 ₽/мес приемлем; оплата только из РФ в рублях; токен за рубежом допустим;
ручное восстановление в бете допустимо; каналы публичные; задержка «пост на сайте за минуту» достаточна.

## 1. Вывод по доказательствам

**Что установлено.**
- Telegram пытается доставить событие: `pending_update_count = 1`, `last_error_message: Connection timed out`.
- Запрос доходит до сервера: в tcpdump есть SYN от `91.108.5.35`, сервер отвечает SYN-ACK.
- Рукопожатие не завершается: ACK не приходит, до TLS и HTTP дело не доходит. Ядро пакеты не отбрасывало.
- Сервер исправен: сайт и `/health` доступны извне, POST без секрета получает 401 от Express, файрвол не настроен.
- В обратную сторону тоже плохо: запросы с VPS к Telegram API падают частично (`ETIMEDOUT`, `ENETUNREACH`).

**Что из этого следует.** Ошибка не в коде приложения и не в настройке сервера. Связь рвётся на сети между
подсетями Telegram и этим VPS, в обе стороны. Обычные клиенты из интернета сервер видят нормально.

**Чего мы не знаем.** Где именно теряются пакеты (у Timeweb, у магистрального оператора, на оборудовании фильтрации),
каким механизмом и надолго ли. Версия «ограничения Telegram в РФ» согласуется с картиной и с публичными сообщениями
других разработчиков о той же ошибке на российских хостингах
([Хабр](https://habr.com/ru/articles/1088102/), [vc.ru](https://vc.ru/id5779154/2795944-blokirovka-telegram-api-v-rossii)),
но для этого сервера она не доказана. Специфичность для Timeweb тоже не исключена и не проверена.

**Практический вывод.** Причину выяснять необязательно. Точку приёма надо вынести туда, где связь с Telegram проверена,
а российский сервер вообще не должен обращаться к Telegram: ни за событиями, ни за фотографиями.

## 2. Варианты

Цены — раздел 5. «Доп. в месяц» — сверх текущего VPS.

| | Вариант | Путь события | Доп. в месяц | Плюсы | Ограничения и отказы |
|---|---|---|---|---|---|
| **А** | Приёмник за рубежом, сам отправляет на сервер в РФ | Telegram → приёмник (журнал на диске) → HTTPS POST на `tg4you.ru` | ≈ 1 820 ₽ | Приёмнику не нужны домен, сертификат и открытые порты. На сервере в РФ nginx не меняется | Зависит от связи «зарубежный хостинг → РФ». Токен бота лежит за рубежом |
| **Б** | Приёмник с очередью, сервер в РФ забирает сам | Telegram → приёмник (очередь) ← HTTPS GET с сервера в РФ | ≈ 1 820 ₽ | На сервере в РФ нет нового входа снаружи. Удобно, когда потребителей станет несколько (сайты клиентов) | Приёмнику нужны поддомен, сертификат, веб-сервер, защита публичного входа. Компонентов больше |
| **В** | Перенос всего Зеркала за рубеж | Telegram → приложение за рубежом → база | ≈ 2 860 ₽ и выше | Одна площадка, нет межсерверной доставки | Сайты для российской аудитории на зарубежном IP: риск замедления и блокировки. База с почтой пользователей: либо остаётся в РФ (каждый запрос через границу), либо переезжает (вопрос локализации персональных данных, 152-ФЗ). Текущий VPS не дешевеет: на нём остаётся Word2you |
| **Г** | Ничего не покупать: сервер в РФ сам опрашивает Telegram (long polling) | Сервер в РФ → `getUpdates` → база | 0 ₽ | Ноль новых компонентов. Событие не теряется, пока хоть один запрос проходит раз в 24 часа | Опирается на канал, который уже падает (`ENETUNREACH`). Задержка непредсказуема, фото — тем же ненадёжным путём. Гарантий нет. Годится как замер и аварийный запасной путь |
| **Д** | Бессерверный приёмник (Cloudflare Workers + D1), сервер в РФ забирает | Telegram → Worker → D1 ← сервер в РФ | 0 ₽ | Бесплатно, без сервера | Доступность Cloudflare из РФ под вопросом (не проверял, публично сообщалось о замедлении). Фото хранить негде без платного R2. Привязка к одному зарубежному сервису с отдельным аккаунтом |

Отброшено без детального разбора: писать с приёмника прямо в PostgreSQL в РФ (учётные данные базы за рубежом, базу надо открывать наружу);
разбор публичной страницы `t.me/s/<канал>` (тот же домен Telegram, нестабильная вёрстка, не работает для закрытых каналов);
клиентский API Telegram (MTProto) под учётной записью пользователя (другой уровень рисков и сложности).

### Webhook или long polling на приёмнике

| | Webhook | Long polling (`getUpdates`) |
|---|---|---|
| Что нужно приёмнику | Публичный HTTPS: домен или IP, сертификат, порт 443/80/88/8443 | Только исходящие соединения |
| Подтверждение | HTTP 200 после записи на диск, иначе не-2xx | Сдвиг `offset` после записи на диск |
| Поверхность атаки | Открытый вход, нужна проверка секрета | Входа нет |
| Второй экземпляр | Переключается сменой URL | Нельзя опрашивать одним токеном из двух мест (ошибка 409) |
| Задержка | Секунды | Секунды (долгий запрос на 50 с) |
| Тихий отказ | Виден в `getWebhookInfo` | Не виден снаружи, нужен свой сигнал «я жив» |

Выбираю **long polling**: у приёмника не остаётся ни одного открытого входа, кроме SSH, и модель «сначала сохранил — потом подтвердил»
получается естественно. Цена выбора: резервный приёмник может быть только холодным (запускается вручную), и нужен внешний контроль «жив ли опрос».

Переключение основного бота с webhook на опрос — одно действие `deleteWebhook` **без** `drop_pending_updates`.
Пока webhook установлен, `getUpdates` не работает; накопленные события (до 24 часов) при снятии webhook сохраняются.

## 3. Рекомендуемая архитектура: вариант А с long polling

Простейшее достаточное решение: **один маленький зарубежный сервер, один процесс, один файл SQLite**.
Сервер в РФ получает готовые события и готовые файлы и с Telegram не разговаривает совсем.

```
Telegram-канал
   │  channel_post / edited_channel_post
   ▼
Telegram Bot API  (хранит неполученные события не дольше 24 часов)
   ▲
   │ getUpdates (исходящий HTTPS с приёмника, долгий запрос 50 с)
   │ getFile + скачивание фото
┌──┴───────────────────────────── ПРИЁМНИК (вне РФ, 1 vCPU / 1 ГБ) ──┐
│ 1. получил пачку событий                                           │
│ 2. записал сырые события и новый offset в SQLite одной транзакцией │
│ 3. только следующий getUpdates с новым offset подтверждает Telegram│
│ 4. скачал фото на диск (повторы, таймауты)                         │
│ 5. отправил фото и событие на сервер в РФ, по порядку              │
│ 6. пометил «доставлено» после ответа 200                           │
│ раз в минуту — сигнал «жив» со счётчиками очереди                  │
└──┬─────────────────────────────────────────────────────────────────┘
   │ HTTPS POST https://tg4you.ru/telegram/ingest/...  (подпись HMAC, проверка сертификата)
   ▼
nginx (уже проксирует /telegram/ на 3100 — конфигурация не меняется)
   ▼
tg4you-api (Express): проверка подписи → одна транзакция:
   запись в telegram_events (ключ bot_id + update_id) → канал → пост с защитой порядка
   ответ 200 только после фиксации в базе
   ▼
PostgreSQL (как сейчас) + файлы /var/www/tg4you.ru/shared/uploads/telegram (как сейчас)
   ▼
API → Next.js → сайт
```

### 3.1. Подтверждение, повторы, дубли

- **Сохранение до подтверждения.** Приёмник пишет сырое событие и `offset = max(update_id) + 1` в одной транзакции SQLite
  (`journal_mode=WAL`, `synchronous=FULL`). Telegram считает пачку полученной только при следующем `getUpdates` с этим `offset`.
  Падение между записью и следующим запросом даёт повторную выдачу, не потерю.
- **Дубли на приёмнике.** `update_id` — первичный ключ, вставка `INSERT OR IGNORE`.
- **Дубли на сервере в РФ.** Таблица `telegram_events` с ключом `(bot_id, update_id)`. Повтор возвращает 200 `duplicate` без изменений.
- **`update_id` ненадёжен на длинной дистанции:** после недели тишины следующий идентификатор выбирается случайно
  (документация Bot API). Поэтому он используется для дедупликации и как последний аргумент при равенстве, а не как версия поста.
- **Идентификатор поста** остаётся прежним: `channel_id + telegram_message_id`.

### 3.2. Порядок и защита от замены нового старым

- Приёмник отправляет события строго по возрастанию `update_id`, по одному (на бете — один последовательный поток).
- На сервере в РФ у поста появляется версия: `version_ts` = `edit_date` для правки, `date` для нового поста, и `source_update_id`.
  Upsert применяется, только если входящая версия не старше сохранённой; при равенстве побеждает больший `update_id`.
  Старое событие возвращает 200 `stale` и ничего не меняет.
- Правка не трогает фото, если `file_unique_id` тот же. Это закрывает находку № 6.

### 3.3. Фотографии

- Скачивает только приёмник: `getFile` → загрузка с таймаутом 30 с → файл `<file_unique_id>.jpg` + SHA-256.
- Ссылка `getFile` живёт не меньше часа; при истечении приёмник запрашивает её заново. Лимит Bot API на скачивание — 20 МБ.
  (Оба числа — из документации Bot API, агент должен сверить дословно.)
- Повторы скачивания: 5 с, 30 с, 2 мин, 10 мин, дальше раз в час до 24 часов. Потом фото помечается «не удалось», пост живёт без него, событие видно в мониторинге.
- **Текст не ждёт фото.** Если фото не готово за 2 минуты, событие уходит с `media: pending`. Сервер в РФ публикует текст.
  Когда фото доедет, оно привязывается к посту по `file_unique_id`. Порядок прихода фото и события не важен.
- На сервер в РФ фото приходит отдельным запросом `PUT /telegram/ingest/media/<file_unique_id>` с контрольной суммой.
  Запись через временный файл и переименование. Лимит тела в nginx сейчас 10 МБ — для сжатых фото Telegram хватает.
- На приёмнике файл хранится 7 дней после подтверждения доставки, затем удаляется.

### 3.4. Очередь, сроки, dead-letter

| Что | Где | Срок |
|---|---|---|
| Неполученные события | Telegram | ≤ 24 ч, не управляется |
| Сырые события, недоставленные | SQLite на приёмнике | Без срока, пока не доставлены |
| Сырые события, доставленные | SQLite на приёмнике | 30 дней (для повторной отправки) |
| Сырые события, принятые | `telegram_events` в PostgreSQL | 90 дней (для переобработки) |
| Dead-letter | SQLite на приёмнике | До ручного разбора |

- Временный отказ (таймаут, 5xx, 429): повтор с ростом паузы 1 с → 2 с → … → 5 мин, со случайной добавкой. Число попыток не ограничено. Очередь стоит, порядок сохраняется.
- Постоянный отказ (422 «не могу разобрать»): после 5 попыток событие уходит в dead-letter, очередь идёт дальше. Сигнал в мониторинг.
- 401/403 (подпись не принята): это ошибка настройки, не события. Очередь стоит, повтор раз в 5 минут, тревога сразу.
- Таймауты: `getUpdates` 50 с + 10 с запаса; отправка события 15 с; отправка фото 60 с.
- Ограничение частоты: на бете один поток. К Telegram — не чаще одного `getFile` в секунду.

### 3.5. Защита соединения между приёмником и сервером в РФ

- Обычный HTTPS с полной проверкой сертификата `tg4you.ru`. Проверку не отключаем нигде.
- Подпись каждого запроса: `HMAC-SHA256(секрет, timestamp + "." + метод + "." + путь + "." + sha256(тело))`.
  Заголовки: идентификатор ключа, время, подпись.
- Повторное воспроизведение: запрос старше 5 минут отклоняется. Внутри окна повтор безвреден: обработка идемпотентна и защищена версией.
- Ротация без простоя: сервер в РФ принимает два ключа одновременно (текущий и следующий). Порядок: добавить новый в РФ → переключить приёмник → убрать старый.
- Старый вход `/telegram/webhook` остаётся с существующей проверкой секрета, но закрывается при пустом секрете (находка № 2) и возвращает 500 при ошибке (находка № 1).
- Дополнительно, позже: ограничение входа `/telegram/ingest` по IP приёмника на уровне приложения.

### 3.6. Что где лежит

| Площадка | Данные | Секреты |
|---|---|---|
| Приёмник (вне РФ) | Сырые события каналов 30 дней, фото 7 дней. Персональных данных пользователей сервиса нет | Токен основного бота, секрет подписи, адреса сигналов мониторинга |
| Сервер в РФ | Всё как сейчас + таблица `telegram_events` | Секрет подписи (текущий и следующий). Токен бота после переключения не нужен, убирается |
| PostgreSQL | Как сейчас: пользователи, каналы, посты | — |
| Мониторинг | Только факт «жив / не жив» | — |

Почта и учётные записи пользователей не покидают РФ. Через границу проходит только содержимое постов, которое автор сам публикует.
Для закрытых каналов это уже нетривиально — отсюда вопрос № 3.

Если токен утечёт, злоумышленник сможет читать события бота и действовать от его имени в каналах в пределах выданных прав.
Мера: просить владельцев каналов давать боту минимальные права администратора (без публикации и удаления); перевыпуск токена у @BotFather.

### 3.7. Наблюдаемость

- Приёмник раз в минуту отправляет на сервер в РФ сигнал со счётчиками: глубина очереди, возраст старейшего недоставленного события,
  время последнего успешного `getUpdates`, время последнего события, число фото в ожидании, число dead-letter.
- Сервер в РФ отдаёт `/health/telegram`: «ok», если сигнал свежее 3 минут и старейшее событие моложе 10 минут. Наружу — только статус, без подробностей.
- Внешний монитор (UptimeRobot, бесплатно) проверяет `/health` и `/health/telegram` раз в 5 минут.
- Независимый сигнал от приёмника в healthchecks.io (бесплатно): если приёмник молчит 5 минут — письмо. Это ловит случай «сервер в РФ лежит, и некому показать, что приёмник жив».
- Уведомления — на почту. Только в Telegram нельзя: это и есть ненадёжный канал.
- «Давно не было постов» не отличить от «сломалось» без контрольного поста. Позже: раз в сутки тестовый бот пишет в `@test_site_tele`, монитор ждёт пост на сайте.

### 3.8. Сценарии отказа и границы гарантий

| Событие | Что происходит | Потеря |
|---|---|---|
| Сервер в РФ недоступен (минуты–дни) | Приёмник копит в SQLite и повторяет. После восстановления досылает по порядку | Нет, пока цел диск приёмника |
| Приёмник упал, перезапустился | systemd поднимает; события лежат в Telegram | Нет, если простой < 24 ч |
| Приёмник недоступен > 24 ч | Telegram выбрасывает события старше 24 ч | **Да.** Восстановление: автор правит пост — приходит `edited_channel_post`, пост появляется. Импорта истории в MVP нет |
| Диск приёмника потерян | Новый приёмник с пустой базой получает от Telegram всё неподтверждённое. Сервер в РФ отсекает дубли | Только события, уже подтверждённые Telegram, но ещё не доставленные в РФ (двойной отказ) |
| Локация или провайдер приёмника теряет связь с Telegram или с РФ | Поднять приёмник у другого провайдера: тот же код, тот же токен, старый остановить | Нет, если уложиться в 24 ч. Домены и DNS не участвуют |
| Домен `tg4you.ru` недоступен | Приёмник копит. Адрес доставки меняется в одном файле | Нет |
| «Ядовитое» событие | Dead-letter после 5 попыток, очередь идёт дальше | Одно событие до ручного разбора |
| Утечка токена или секрета | Перевыпуск токена, ротация ключа | — |
| Telegram недоступен целиком или бот заблокирован | Ничего не приходит | Не лечится архитектурой |
| Связь «зарубежный хостинг ↔ РФ» ограничена целиком | Вариант А и Б не работают оба | Не лечится этой архитектурой |

**Чего я не обещаю:** работу «при любых ограничениях»; доставку удалений постов; сохранность при простое приёмника дольше суток;
стабильность выбранной локации на годы. Обещание в границах: при исправном приёмнике и простое сервера в РФ любой длительности
(в пределах диска) посты не теряются и не перезаписываются старыми версиями.

### 3.9. Резервные копии и повторная обработка

- База PostgreSQL и папка с фото — как сейчас в `docs/deploy.md`. Таблица `telegram_events` попадает в ту же копию.
- Приёмник: копия не обязательна на бете (он восстанавливается с нуля). Опционально — ежедневная копия диска у провайдера.
- Повторная отправка с приёмника: команда `relay replay --from <update_id> --to <update_id>` сбрасывает отметку «доставлено».
- Переобработка на сервере в РФ: команда `npm run telegram:reprocess -- --from … --to …` заново применяет события из `telegram_events`.
  Обе операции безопасны благодаря защите версией.

### 3.10. Когда решение придётся усложнять

| Порог | Что добавить |
|---|---|
| Платные клиенты или ~50 каналов | Холодный резервный приёмник у другого провайдера, ежедневная копия SQLite, контрольный пост раз в сутки |
| Публикация на сайтах клиентов | Выдача событий наружу по схеме Б (клиентские сайты забирают сами). Журнал `telegram_events` для этого уже есть |
| ~500 каналов | Фото в S3, параллельная доставка по каналам с сохранением порядка внутри канала, автоматическое переключение на резерв |
| Тысячи событий в минуту | Webhook вместо опроса, PostgreSQL вместо SQLite на приёмнике, несколько экземпляров |

## 9. Критерии приёмки, риски, открытые вопросы

### Приёмка (на тестовом боте, затем на основном)

1. Пост с текстом появляется на сайте быстрее 60 с; пост с фото — быстрее 2 минут, фото открывается.
2. Сервер `tg4you-api` остановлен на 30 минут, за это время сделано 5 постов и 2 правки → после запуска все 5 на сайте, тексты последние, дублей нет.
3. Приёмник убит в момент обработки (`kill -9`) → после перезапуска ни одного потерянного и ни одного задвоенного поста.
4. Одно и то же событие отправлено 3 раза → в базе одна запись, ответы `applied`, `duplicate`, `duplicate`.
5. Старое событие отправлено после правки → текст на сайте не изменился, ответ `stale`.
6. Запрос с неверной подписью и запрос старше 5 минут → 401, в базе ничего.
7. Сбой скачивания фото (отключён доступ к Telegram на приёмнике на 5 минут) → текст опубликован сразу, фото доехало после восстановления.
8. Правка подписи у поста с фото → фото на месте.
9. Остановка приёмника → письмо от мониторинга не позже чем через 10 минут.
10. За всё время работ Word2you отвечает, процесс `myworld-server` не перезапускался, его конфигурация nginx не менялась.
11. Семь дней наблюдения на основном боте: ни одного расхождения между каналом и сайтом, dead-letter пуст.

### Риски

| Риск | Вероятность | Что делаем |
|---|---|---|
| Связь «зарубежная локация ↔ РФ» ухудшится | Не оценить | Эксперимент Э3; холодный резерв у другого провайдера; переход на схему Б при асимметрии |
| Ограничения Telegram в РФ усилятся | Не оценить | На доставку не влияет: приёмник вне РФ. Влияет на сам продукт — см. ниже |
| Простой приёмника > 24 ч | Низкая при мониторинге | Тревога за 5–10 минут, восстановление с нуля за час, ручная правка постов |
| Утечка токена бота с зарубежного сервера | Низкая | Минимальные права бота в каналах, вход только по SSH-ключу, перевыпуск токена |
| Поломка Word2you при релизе | Низкая, цена высокая | nginx не трогаем; перезапускается только `tg4you-api`; миграция только добавляет таблицы и столбцы |
| Рост цен хостинга | Средняя | Приёмник переносим за час, привязки к провайдеру нет |
| Условия провайдера и право | Не оценено | Ниже |

### Вопросы данных и условий провайдеров (не юридическая консультация)

- Персональные данные пользователей сервиса (почта, учётные записи) остаются в РФ — в этом смысл выбора А вместо В.
- За рубежом временно лежит содержимое постов. Для публичных каналов это уже опубликованный материал.
  Для закрытых каналов стоит явно написать в условиях сервиса, что публикации обрабатываются на серверах за пределами РФ.
- В постах могут встречаться персональные данные третьих лиц (подпись автора, упоминания). Нужно ли это отражать в политике обработки данных — вопрос к юристу.
- Статус Telegram в РФ может измениться. Как это повлияет на сервис, который забирает из него публикации, — вопрос к юристу, я на него не отвечаю.
- Перед покупкой прочитать правила провайдера о размещаемом ПО. Приёмник — обычный клиент Bot API, не прокси и не VPN для пользователей.

### Наблюдение о продукте (вне задания, но влияет на ставку)

Если доступ к Telegram в РФ ухудшается, ценность «сайт-зеркало канала» для авторов растёт: сайт открывается там, где Telegram — нет.
Одновременно растёт зависимость от единственной точки приёма. Это довод сделать резервный приёмник раньше, чем появятся платные клиенты.
